7/*!
8Unsafe code information.
9
10Some features need capabilities only unlocked by `unsafe` code.
11Unsafe code is tested by Miri where possible. It cannot execute all valid
12Rust code, so some tests need to be left uncovered. Please open an issue or
13PR for any unsound use of `unsafe`. The isolation of unsafe code to only
14the explicitly unsafe features is guarded by a conditional
15`forbid(unsafe_code)` in the crate root.
16
17# Safe Features
18* `array`
19* `directory`
20* `async`
21* `bincode`
22* `serde_json`
23* `simd_json`
24* `csv`
25* `async_bincode`
26* `async_csv`
27* `zstd`
28* `zstdmt`
29* `async_zstd`
30* `async_zstdmt`
31* `network`
32
33# Unsafe Features
34See documentation and comments in the feature function/structs for
35finer-grained justifications.
36
37### `unsafe_array`
38The `generic` methods are premised on the guarantees of
39[`StableDeref`](stable_deref_trait::StableDeref). Mainly, we can borrow
40from the storage pointed to by a container even if the container itself is
41moved on stack. `unsafe` is needed to keep the container handles alive as
42long as their referenced data is considered valid, but also allow the
43handles to move.
44
45The mutable iterators also need `unsafe`. The nature of a one-way iterator
46is that the accesses to each element in the container are unique, but this
47borrowing is outside of the slice API. So unsafe pointers are needed to
48give out the exclusive mutable element access.
49
50The complex iterators that save storage or flush on drop also `unsafe`, so
51that the last instance of the handle can perform mutable cleanup. The
52shared mutable element is not modified besides creation and cleanup.
53
54### `tokio` & `smol`
55Due to [`std::mem::forget`], scoped async blocks are inherently unsafe. The
56runtime execution options provided for runtime executors rely on scoped
57async blocks, so need to expose an `unsafe` function for them.
58
59### `mmap`
60All mmap APIs are unsafe, due to the possibility of an external process
61modifying the file. `unsafe` is also used for mutable mmaps, so that it can
62be preserved after the write handle is dropped but enforce mutability rules
63at runtime. Otherwise the mmap would be pointlessly read again from disk
64when the write handle is dropped and read handles are opened.
65
66### `encrypted`
67[`Bytes`][`secrets::traits::Bytes`] needs an unsafe block to extend a blanket implementation.
68[`Send`] and [`Sync`] standard library *lints* around pointers (not necessarily protecting from
69unsafe behavior, just the potential of pointer hackery that breaks those rules) also need unsafe to bypass.
70
71There is also a use of [`BorrowExtender`][`crate::utils::BorrowExtender`] that requires a bit of lifetime
72hacking to match the valid lifetime of the borrow.
73
74### `network`
75Implementing [`Send`] and [`Sync`] on a [`UnsafeCell`][`std::cell::UnsafeCell`] wrapping type.
76[`UnsafeCell`][`std::cell::UnsafeCell`] is used to work around mutability problems in reading the [`reqwest`] response.
77
78*/
